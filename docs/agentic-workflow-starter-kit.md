# Agentic Workflow Starter Kit

AI 코딩 에이전트와 함께 저장소를 바꿀 때, 다른 저장소로 옮겨도 그대로 쓰는 **최소 문서 세트와 검증 루프**다. 특정 도메인·언어·파일 이름에 묶이지 않도록 원칙만 적는다. 이 저장소에서 20개 lab을 거치며 실제로 효과가 있었던 것만 남겼다.

## 1. 기준 문서 (에이전트가 먼저 읽는 것)

| 문서 | 역할 | 최소 내용 |
| --- | --- | --- |
| 루트 에이전트 지침 (`AGENTS.md` 같은 한 파일) | 모든 작업의 시작점 | 읽기 순서, 실행·검증 명령, 금지 규칙(승인 없는 정책 확정 금지, 오류를 삼키는 fallback 금지, 테스트 없는 상태 변경 금지, 외부 부작용 금지), 최종 보고에 넣을 것(실행한 명령과 결과, 미실행 검증, 남은 위험) |
| 도메인 정책 문서 (영역별 1개) | 에이전트가 임의로 정하면 안 되는 규칙 | 상태 정의와 전환표(허용·금지·보류), 다른 정책과의 책임 경계, **확정된 응답·값**, **보류 사항**(사람 결정 전 구현 금지), 근거 링크 |
| 산출물 위치 규약 | 문서가 흩어지지 않게 | 오래 사는 기준(`docs/`) / 이번 작업의 기록(`notes/`) / 플랫폼이 읽는 설정(`.github/`)의 구분과 이름 규칙 |
| 결정 기록 | 사람이 내린 선택의 원장 | 질문, 선택지, 처리 상태, 실제 선택, 적용 위치. 보류 항목도 여기에 |

원칙: 정책에 **없거나 보류된** 것은 에이전트가 멈추고 묻는다. 「확정」 절과 「보류」 절을 분리해 두면 그 판단이 기계적으로 가능하다.

## 2. 요청 → 계획 → 승인 (plan-first)

1. **요청 원문을 보존**한다. 해석으로 바꾸지 않고, 완료 조건을 요청자의 말로 적는다. 요청 출처가 Issue면 Issue가 유일한 원문이다.
2. **현재 동작을 먼저 재현**한다. 재현되지 않으면 그 사실이 첫 발견이다(요청이 다른 코드 상태를 전제했을 수 있다).
3. **계획**에는 파일별 「바꾼다 / 건드리지 않는다」, 각 변경의 근거(요청 문장 또는 정책 문장), 검증 계약(시나리오 + 명령 + 통과·정지 기준), 「사람 결정 필요」가 들어간다. 선택지는 적되 선택하지 않는다.
4. **사람 승인**은 계획 파일에 승인자·시각·답을 적어 남긴다. 승인 전에는 코드를 바꾸지 않는다.

흔한 실패: 계획 문서가 둘 이상으로 갈라져 「어느 계획이 지배하는가」를 reviewer가 되묻게 된다. 한 변경에는 승인된 계획 하나만 둔다.

## 3. 역할 분리 (planner · implementer · reviewer)

| 역할 | 입력 | 출력 | 금지 |
| --- | --- | --- | --- |
| planner | 요청, 정책, 현재 코드(읽기), 결정 기록 | 승인 가능한 계획 | 코드 수정, 보류 확정, 요청 밖 개선 |
| implementer | 승인된 계획 | 범위 안의 변경 + 실행한 검증 결과 원문 | 계획 밖 수정, 실패 테스트의 기대값 수정, fallback 추가 |
| reviewer | 요청·계획·diff·테스트·정책 | 종류별 발견 사항(계획 이탈 / 정책 이탈 / 테스트 누락 / 민감정보 / 질문), 심각도, 근거 줄 | 직접 수정, 근거 없는 판정, 「전부 괜찮음」 한 줄 |

역할 이름만 바꾸는 것은 효과가 없다. **입력을 다르게 주고(기준 커밋·승인 기록·diff 범위), 금지를 다르게 걸어야** 다른 결과가 나온다. 이 저장소에서는 같은 변경을 단일 세션으로 했을 때 보이지 않던 「계획에 없는 변경 9건」과 「테스트 0건인 경로」가 역할 분리에서 드러났다.

## 4. 검증 루프

- **결정적 명령 세트**를 고정한다(예: 테스트 · 타입 검사 · 정적 검사 · 저장소 자체 점검). 구현 직후와 머지 직후에 같은 세트를 돌리고 결과 원문을 기록한다.
- **시나리오 ↔ 테스트 1:1 매핑**을 계획에 적고, reviewer가 「테스트 이름」으로 확인한다. 「통과했다」가 아니라 「어떤 테스트가 어떤 경로를 보호한다」가 증거다.
- **정확값 단언**: 정책이 확정한 응답(상태 코드·본문·필드 값)은 `not 200` 같은 느슨한 단언이 아니라 정확값으로 고정한다. 느슨한 단언은 정책 표류를 통과시킨다.
- **민감정보는 부정 단언**으로: 모든 응답·저장소·로그에 토큰·키·내부 예외가 없음을 식별 가능한 고유 문자열로 검사한다.
- **데이터 불변식**은 저장소 직접 조작으로도 검사한다. API 경로로 만들 수 없는 상태(정책이 막은 전환)가 데이터로는 생길 수 있다.
- 테스트가 실패하면 기대값을 고치지 않는다. 실패 원문을 남기고 「구현이 틀렸나, 기대가 정책과 다른가」를 사람이 판단한다.

## 5. Issue 기반 시작

- Issue 템플릿에 Summary / Context / Current Behavior(재현 절차) / Expected Behavior / Scope / Out of Scope / Acceptance Criteria(관찰 가능한 참·거짓) / Human Decision Needed / References를 둔다.
- 기대 동작이 정책과 충돌하면 **기대를 확정하지 않고** 사람 결정으로 올린다. 고객 요구를 그대로 기대 동작에 쓰지 않는다.
- 탐색은 Issue만 입력으로 받아 재현 → 근거 경로(정책 문장·코드 위치·테스트 이름) → 사실/가설 분리 → 미확인 순으로 코멘트 초안을 만들고, **게시 전에 사람이 본다**.
- 민감정보(고객 식별 정보, 결제 토큰)는 Issue에 넣지 않는다. 공개 저장소면 더욱.

## 6. Automation 연결

- 후보는 **두 번 이상 같은 입력·같은 검증으로 반복한 일** 중에서만 고른다. 새 기능을 보여 주려고 만들지 않는다.
- 각 후보에 Input / Output / Run Condition / Stop Condition / Human Approval / Failure Alert 여섯 필드를 채운다. 자동 실행은 **읽기 전용**이고, 커밋·푸시·코멘트·머지 같은 외부 변경은 사람 승인 뒤에만 한다.
- 예약 전에 **같은 프롬프트로 한 번 수동 실행**해 결과를 기록한다.
- 중단 조건 다섯 가지(반복 실패 · 범위 확장 · 권한 부족 · 데이터 부족 · 외부 상태 변경)마다 감지 신호, 보존할 상태, 알림, 재개 주체, **재시도 상한**을 둔다. 무한 재시도는 없다.
- Surface는 가장 작은 것부터: 명령으로 판정되면 CLI, 웹 화면이 필요하면 Browser, 전용 연동이 없는 GUI만 Computer Use, 계획·리뷰는 대화형 앱.

## 7. 장애 대응 (incident)

1. VOC와 로그에서 **직접 읽은 사실**과 **추정**을 분리하고, 고객 영향과 운영 영향을 따로 적는다.
2. 원인 후보는 **층별로**(외부 · 결제/데이터 · 상태 · 표시) 세 개 안팎을 세우고, 각 후보에 **반증 가능한 확인 방법**을 붙인다.
3. 수정 / rollback / 추가 조사를 증거로 고른다. 증상을 숨기는 수정(이력 삭제 등)은 선택지에서 뺀다.
4. 고친 뒤에는 **회귀 테스트**가 그 경로를 보호하는지 확인한다. 「코드가 이미 맞다」와 「테스트가 지킨다」는 다르다.
5. PR 기록에 Risk와 Rollback 절차를 적는다.

## 8. 사람이 판단하는 것 (자동화하지 않는다)

- 정책의 확정과 변경, 보류 항목의 해제
- 범위 변경과 계획 승인
- reviewer 발견 사항의 처리(수정 / 범위 밖으로 기록 / 무시)
- 머지, 배포, 외부 공개(Issue·PR 코멘트 게시 포함)
- 민감정보 경로의 「괜찮다」 판정

## 옮길 때의 최소 세트

새 저장소에 처음 넣는 것: 루트 에이전트 지침 1개, 도메인 정책 1개 이상(확정/보류 절 분리), 산출물 위치 규약, 결정 기록 파일, 역할 프롬프트 3개, Issue 템플릿, 검증 명령 세트, 중단 조건 표. 나머지는 첫 작업을 하면서 `notes/`에 쌓인다.

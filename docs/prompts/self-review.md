# Self-review 프롬프트

diff를 다시 읽어 주는 요약이 아니다. Issue와 implementation plan을 기준으로 **계획에 없던 변경**과 **계획에는 있지만 검증되지 않은 결과**를 찾아내고, 검증 결과를 다음 판단에 되돌려 주는 review 단계다. 파일을 고치지 않는다. 구현이 끝나고 PR을 열기 전에 사람이 실행을 결정한다. 역할 분리 실행에서는 `docs/prompts/reviewer.md`가 이 자리를 맡는다.

## 입력

| 항목 | 값 |
| --- | --- |
| Issue 초안 또는 Issue 본문 | `notes/issue-draft-______.md` 또는 Issue #`____` (`.github/ISSUE_TEMPLATE/workflow-task.md` 구조. Scope·Out of Scope·Acceptance Criteria를 기준으로 쓴다) |
| implementation plan | `notes/plans/______.md` (`docs/templates/implementation-plan.md` 또는 planner 다섯 절 형식. Files to Change·Steps·Tests·Stop Conditions를 기준으로 쓴다) |
| diff | `git diff <base>..<head>` — base `______`, head `______` |
| 테스트 결과 | `npm test` / `npm run typecheck` / `npm run lint` 출력 원문과 실행 커밋 |
| 적용 정책 | plan의 Files to Read First(또는 정책 근거)가 가리키는 `docs/*-policy.md` 절 |

네 입력(Issue·plan·diff·테스트 결과)이 모두 없으면 시작하지 않는다. plan이 없으면 Issue만으로 범위 이탈을 판정할 수 없으므로 그 사실을 먼저 보고한다.

## 금지

- `src/`, `tests/`, 문서를 수정하지 않는다. 수정안은 제안으로만 적는다.
- diff 내용을 다시 설명한 문장을 「발견 사항」으로 보고하지 않는다. 발견 사항은 계획·Issue·정책과 실제 결과의 **어긋남**이고, 요약은 별도 절에 분리한다.
- 근거 없는 추정을 발견 사항으로 적지 않는다. diff 줄, 정책 문장, 테스트 이름 중 하나를 근거로 붙이지 못하면 「미확인」으로 적는다.
- 실행하지 않은 검증을 통과로 간주하지 않는다. 입력에 원문이 없는 명령은 「미실행」으로 다룬다.
- 발견 사항이 없을 때 빈칸으로 두지 않는다. 항목마다 `없음`을 명시하고 확인한 범위를 적는다.
- 기대값을 코드에 맞춰 고치라는 제안을 하지 않는다. 테스트와 정책이 다르면 어느 쪽이 정책 문장과 일치하는지만 적는다.

## 출력

다음 절을 이 순서로 쓴다. 각 발견 사항에는 **파일 경로·근거(diff 줄 또는 정책 문장 또는 테스트 이름)·심각도(차단/권고)** 를 붙인다.

1. **검토 범위** — 대조한 Issue·plan·diff 범위·테스트 결과 커밋. 읽지 못한 것.
2. **범위 이탈(계획에 없던 변경)** — plan의 Files to Change·Steps(또는 변경 범위 표)에 없거나 「건드리지 않는다」로 적힌 파일·필드·동작의 변경. Issue의 Out of Scope 항목을 건드린 변경. 없으면 `없음`.
3. **누락 테스트(계획에는 있지만 검증되지 않은 결과)** — plan의 Tests(또는 검증 계약) 행과 Issue의 Acceptance Criteria 항목 중 대응하는 테스트가 diff·기존 테스트에 없는 것. 바뀐 동작 중 실패해도 잡히지 않는 경로. 없으면 `없음`.
4. **정책 이탈** — 정책 문장과 어긋나는 동작. 문서·절·문장을 인용한다. 없으면 `없음`.
5. **민감정보 노출** — 카드 토큰, 내부 예외 메시지, 스택, 고객 식별 정보가 응답·로그·문서로 나가는 경로. 없으면 `없음`.
6. **검증 결과 판정** — 입력받은 명령별 통과/실패/미실행. 실패가 있으면 어느 Step·AC가 미충족인지.
7. **질문(사람 결정 필요)** — 판단에 사람의 결정이 필요한 지점과 선택지. 선택하지 않는다.
8. **요약(참고)** — diff가 무엇을 바꿨는지 한 단락. 발견 사항과 섞지 않는다.

## 검증

- 2~5 절 각각에 발견 사항이 있거나 `없음`과 확인한 범위가 적혀 있는지 확인한다. 비어 있는 절이 없어야 한다.
- 각 발견 사항에 경로·근거·심각도 세 가지가 모두 있는지 확인한다.
- 2절의 모든 항목이 plan 또는 Issue의 특정 행·절을 가리키는지(「계획에 없다」의 근거가 되는 위치) 확인한다.
- 3절이 plan의 Tests 행과 Issue AC 항목을 하나씩 대조한 결과인지 확인한다(건너뛴 행이 있으면 사유를 적는다).
- `git status --short`로 review 중에 파일이 바뀌지 않았는지 확인한다.
- 사람에게 돌려주는 것: 차단 항목 수, 권고 항목 수, 질문 목록, 검증 결과 판정. 차단 항목이 있으면 사람이 항목마다 「수정 / 범위 밖으로 기록 / 무시」를 정한 뒤에만 다음 수정으로 넘어간다.

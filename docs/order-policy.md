# 주문 상태 정책

## 목적과 범위

이 문서는 주문 상태의 의미와 상태 전환 조건을 정의한다. 현재 코드의 동작을 설명하는 문서가 아니며, 구현 범위에 포함되지 않은 상태도 장기 정책의 의미와 전환 경계를 기록한다.

결제 응답 형식과 재고 변경 규칙은 이 문서에서 결정하지 않는다. 해당 책임은 별도의 결제 정책과 재고 정책에서 다루되, 이 문서의 상태 전환과 충돌해서는 안 된다.

## 상태 정의

| 상태 | 의미 | 진입 조건 |
| --- | --- | --- |
| `pending` | 주문이 생성되었고 결제 결과가 확정되지 않은 상태 | 유효한 주문이 생성되어 저장됨 |
| `paid` | 결제가 성공해 주문 금액이 지급된 상태 | `pending` 주문의 결제가 성공하고 결제 완료 조건을 충족함 |
| `payment_failed` | 결제를 시도했지만 실패했으며 실패 이력을 보존하는 상태 | `pending` 주문의 결제 시도가 실패함 |
| `cancelled` | 결제 전에 주문 진행을 취소한 상태 | 결제되지 않은 `pending` 주문의 취소가 승인됨 |
| `refunded` | 결제 성공 뒤 금액 반환이 완료된 상태 | `paid` 주문의 환불 처리가 완료됨 |

`payment_failed` 주문은 실패 원인과 후속 운영 판단을 추적할 수 있도록 삭제하지 않고 보존한다.

## 상태 전환 조건

`허용`은 정책상 사용할 수 있는 전환, `금지`는 요청을 거부해야 하는 전환, `보류`는 사람의 추가 결정 전까지 구현하거나 허용해서는 안 되는 전환을 뜻한다.

| 시작 상태 | 이벤트 | 종료 상태 | 판정 | 조건 또는 근거 |
| --- | --- | --- | --- | --- |
| 주문 없음 | 유효한 주문 생성 | `pending` | 허용 | 생성 조건을 충족한 새 주문만 진입함 |
| `pending` | 결제 성공 | `paid` | 허용 | 결제 완료 조건을 모두 충족해야 함 |
| `pending` | 결제 실패 | `payment_failed` | 허용 | 실패 주문과 실패 이력을 함께 보존함 |
| `pending` | 결제 전 주문 취소 | `cancelled` | 허용 | `cancelled`는 결제 전 주문에만 사용함 |
| `paid` | 금액 반환 완료 | `refunded` | 허용 | 결제 성공 뒤 금액을 되돌린 이력을 남김 |
| `paid` | 주문 취소 | `cancelled` | 금지 | 결제 성공 뒤 처리는 단순 취소가 아니라 환불로 구분함 |
| `payment_failed` | 같은 주문 재결제 성공 처리 | `paid` | 금지 | 실패 주문의 재결제를 허용하지 않기로 승인함 |
| `payment_failed` | 결제 대기 상태로 되돌림 | `pending` | 금지 | 실패 이력을 초기 상태로 덮어쓰지 않음 |
| `cancelled` | 결제 시도 | `paid` | 금지 | 취소된 주문은 결제 가능한 주문이 아님 |
| `cancelled` | 주문 재개 | `pending` | 보류 | 재개 허용 여부와 조건은 사람의 결정이 필요함 |
| `pending` | 결제 전 환불 요청 | `refunded` | 금지 | 지급된 금액이 없으므로 환불 상태로 전환할 수 없음 |
| `paid` | 결제 실패 기록 | `payment_failed` | 금지 | 완료된 결제의 사후 실패를 결제 시도 실패와 섞지 않음 |
| `refunded` | 재결제 또는 결제 복구 | `paid` | 보류 | 환불 뒤 재결제 정책은 아직 결정되지 않음 |
| `refunded` | 주문 취소 | `cancelled` | 금지 | 환불 이력을 단순 취소 상태로 덮어쓰지 않음 |

표에 없는 상태 전환은 아직 판정되지 않은 것으로 보고, 사람의 결정 전까지 보류한다.

상태를 바꾸지 않는 조회와 거부 응답은 전환으로 간주하지 않는다. 금지 또는 보류된 요청은 기존 주문 상태와 보존된 이력을 변경하지 않아야 한다.

## 사람이 승인한 전환 경계

- `paid` 주문은 `cancelled`로 전환하지 않는다. 금액을 되돌릴 때만 `refunded`로 전환한다.
- `cancelled`는 결제 전 `pending` 주문에만 사용한다.
- 결제 성공 뒤에는 금전 처리 이력이 남아야 하므로 단순 취소와 환불을 같은 상태로 섞지 않는다.
- `payment_failed` 주문은 같은 주문으로 재결제하지 않는다.

## 관리자 조회 기준

관리자 주문 목록은 저장된 주문을 기준으로 현재 상태와 운영 판단에 필요한 최소 정보를 제공한다. 결제 실패 정보는 `payment_failed` 주문에만 조건부로 제공하며, 결제 정책이 보존하도록 정한 실패 이력을 사용한다.

### 필수·조건부 정보와 현재 제공 여부

| 분류 | 정보 | 표시 조건 | 현재 제공 여부 | 현재 근거와 목표 차이 |
| --- | --- | --- | --- | --- |
| 필수 | 주문 ID (`id`) | 모든 주문 | 제공 | 현재 관리자 응답이 `Order.id`를 제공함 |
| 필수 | 현재 주문 상태 (`status`) | 모든 주문 | 제공 | 저장된 `Order.status`를 그대로 제공함 (2026-10-16 구현). 실패 이력 존재만으로 상태를 파생하지 않음 |
| 필수 | 주문 총액 (`totalKrw`) | 모든 주문 | 제공 | 현재 관리자 응답이 `Order.totalKrw`를 제공함 |
| 필수 | 주문 생성 시각 (`createdAt`) | 모든 주문 | 제공 | 현재 관리자 응답이 `Order.createdAt`을 제공함 |
| 조건부 | 결제 실패 금액 | `status === "payment_failed"` | 제공 | `failure.amountKrw`로 제공함 (2026-10-16 구현) |
| 조건부 | 결제 실패 시각 | `status === "payment_failed"` | 제공 | `failure.at`으로 제공함 |
| 조건부 | 결제 실패 사유 | `status === "payment_failed"` | 제공 | `PaymentAttempt.failureReason`을 `failure.reason`으로 제공함. 값은 안전한 사유 코드(현재 `card_declined`) |

조건부 정보는 `failure` 객체 하나로 묶어 `payment_failed` 주문에만 붙이며, 일반 주문에 빈 값이나 추정값으로 붙이지 않는다.

### `payment_failed` 주문 표시 조건

- 관리자 목록의 기준은 `orders`에 보존된 주문이다. 결제 실패 주문도 삭제하지 않고 목록에 포함한다.
- `order.status === "payment_failed"`일 때만 관리자 상태를 `payment_failed`로 표시한다. 실패 시도가 존재한다는 이유만으로 `pending`, `paid`, `cancelled` 또는 `refunded` 상태를 실패 상태로 덮어쓰지 않는다.
- 실패 금액·시각·사유는 해당 주문의 실패 결제 이력에서 가져오며, 다른 주문의 이력이나 성공 이력을 결합하지 않는다.
- `payment_failed` 주문에는 실패 금액·시각·사유가 모두 있어야 한다. 주문 상태와 실패 이력이 일치하지 않으면 다른 상태나 임의의 실패 정보로 대체하지 않고 데이터 불일치로 판정한다.
- 데이터 불일치의 판정과 응답 (2026-10-16 확정): `payment_failed` 주문의 실패 이력이 정확히 하나가 아니면(0개, 또는 2개 이상) 불일치다. 재결제가 금지되어 있으므로 2개 이상은 정상 흐름에서 생기지 않는다. 불일치가 있으면 관리자 목록 요청에 `500`과 `{ "message": "Inconsistent payment failure record", "orderId" }`를 반환하고, 내부 예외 메시지는 노출하지 않는다. 여러 이력 중 하나를 고르는 규칙은 만들지 않는다.
- 주문 없이 실패 결제 이력만 남은 경우에는 고아 이력으로 판정하며, 그 이력만으로 관리자 주문 행을 생성하지 않는다. 주문 삭제 자체가 실패 주문 보존 정책 위반이다.

### 노출 제외 정보

| 제외 정보 | 현재 제공 여부 | 기준 |
| --- | --- | --- |
| 카드 정보 | 미제공 | 카드 토큰, 카드 번호, 유효기간, 보안 코드와 카드 식별 정보는 원문·마스킹 여부와 관계없이 관리자 주문 목록에 포함하지 않음 |
| 내부 오류 | 미제공 | 내부 예외 객체, 예외 메시지, 스택 트레이스와 서버 구현 세부 정보는 포함하지 않음 |
| 원시 오류 응답 | 미제공 | 결제 제공자나 내부 시스템의 원시 오류 본문은 포함하지 않음 |

관리자에게 제공하는 결제 실패 사유는 운영 판단에 필요한 안전한 사유 코드나 정제된 설명이어야 하며, 카드 정보·내부 오류·스택 메시지·원시 오류 응답을 포함해서는 안 된다.

### `refunded` 주문 표시 조건 (2026-10-16 확정)

- `order.status === "refunded"`일 때만 환불 정보 `refund { amountKrw, at }`를 붙인다. 환불 이력이 있다는 이유만으로 다른 상태를 덮어쓰지 않는다.
- `refunded` 주문의 환불 이력이 정확히 하나가 아니면 데이터 불일치로 판정하고, 결제 실패 불일치와 같은 방식으로 `500`과 `{ "message": "Inconsistent refund record", "orderId" }`를 반환한다.

### `cancelled` 주문 표시 조건 (2026-10-16 확정)

- `order.status === "cancelled"`일 때만 취소 정보 `cancellation { at }`를 붙인다.
- `cancelled` 주문의 취소 이력이 정확히 하나가 아니면 데이터 불일치로 판정하고 `500`과 `{ "message": "Inconsistent cancellation record", "orderId" }`를 반환한다.

## 취소 전환의 구현 (2026-10-16 확정)

`pending → cancelled` 전환은 `POST /orders/:id/cancel`로 구현한다. 요청 본문은 없다.

- 취소는 `pending` 주문에만 허용한다. `paid`·`refunded`는 금지 전환, `payment_failed`·`cancelled`는 표에 없는 보류 전환이므로 모두 `400 { "message": "Order is not cancellable", "status" }`로 거부하며, 거부는 상태·이력·재고를 바꾸지 않는다. 존재하지 않는 주문은 `404`.
- 성공 응답은 `200`, `{ "ok": true, "order", "cancellation": { "at" } }`이며 취소 시각을 이력으로 보존한다.
- 결제 전 주문은 재고를 차감한 적이 없으므로 취소로 재고가 변하지 않는다([재고 정책](inventory-policy.md)).
- `cancelled` 주문의 결제·환불 요청은 각각 `Order is not payable`·`Order is not refundable`로 거부한다. `cancelled → pending` 재개는 여전히 보류다.

## 환불 전환의 구현 (2026-10-16 확정)

`paid → refunded` 전환은 `POST /orders/:id/refund`로 구현한다. 상세 응답과 재고 처리는 [결제 정책](payment-policy.md)과 [재고 정책](inventory-policy.md)이 정한다. 이 문서가 정하는 것은 다음이다.

- 환불 요청은 `paid` 주문에만 허용한다. `pending`·`payment_failed`·`refunded`·`cancelled` 주문의 환불 요청은 거부하며, 거부는 상태·이력·재고를 바꾸지 않는다.
- `refunded` 주문의 결제 요청은 보류 전환(`refunded → paid`)이므로 결제 가능 주문이 아닌 것으로 거부한다.

## 구현 범위와의 분리

다섯 상태와 허용 전환은 모두 구현되었다. 보류 전환(`cancelled → pending`, `refunded → paid`)은 거부로 남아 있으며, 저장 기술은 이 상태 정책의 결정 범위가 아니다.

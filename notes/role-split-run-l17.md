## 이 저장소의 시작 상태와 Lab 전제의 차이

Lab 17은 「실패 주문은 보존되지만 관리자 응답에 실패 사유가 없고 `deriveDisplayStatus()`가 남아 있는 상태」를 전제한다. 이 fork의 실제 출발점은 달랐다.

| 항목 | Lab 전제 | 이 fork |
| --- | --- | --- |
| Lab 9~16 산출물 | 있음 | 없음 (`node labs/tools/check.mjs 16` 실패 16건) |
| 실패 주문 | 보존됨 | 기준 커밋 `e8c7010`에서는 삭제됨 (v0) |
| 관리자 실패 사유 | 없음 | 2026-10-16 PR #1(`e8c7010..9cb009c`)로 이미 구현·머지됨 |
| `deriveDisplayStatus()` | 유지 | PR #1에서 저장 상태 그대로 표시하는 구현으로 교체됨 |

그래서 E2는 「같은 변경을 두 방식으로」를 다음과 같이 수행했다. 단일 세션 방식은 PR #1을 만든 과정(한 에이전트가 계획·구현·검증을 모두 수행)을 기준선으로 쓰고, 역할 분리 방식은 같은 변경을 기준 커밋 `e8c7010` 시점에서 planner → implementer → reviewer 세 에이전트로 다시 통과시키되 implementer는 새 코드를 쓰지 않고 PR #1의 실제 diff를 승인된 계획과 대조하는 검증 전용으로 돌렸다.

## 단일 세션 방식 (기준선: PR #1, 2026-10-16 오전)

| 단계 | 한 일 | 근거 자료 |

## 역할 분리 방식

### 1. planner

- 입력: 요청(E2), 기준 코드 `git show e8c7010:src/*`, 정책 문서(요청 이후 확정 절은 근거에서 제외), `AGENTS.md`, 이전 승인 계획.
- 출력: `notes/plans/l17-admin-failure-reason.md` — 요청 요약 / 정책 근거 P1~P8 / 파일별 변경 범위 / 검증 시나리오 S1~S7 / **사람 결정 필요 4건**.
- 코드 수정 없음 (`git status -- src tests` 비어 있음 확인).
- planner가 찾아낸 것: Lab 전제와 기준 코드의 불일치(실패 주문 삭제), 정책 P4(`payment_failed` 표시)와 「`deriveDisplayStatus()` 미수정」 제약의 충돌, 기준 시점 정책이 비워 둔 불일치 응답.

### 사람 승인 지점 1 — 계획 승인 (완료)

소유자가 네 결정에 답했다(계획 파일 「승인 기록」). 답은 PR #1 때 확정한 내용과 같다: A-ii(보존 + 402), a(`card_declined`), a(불일치 500, `catch → []` 제거), b(`deriveDisplayStatus()` 정책대로 교체 — Lab 제약 해제). 이 승인이 있기 전에는 implementer를 시작하지 않았다.

### 2. implementer (검증 전용)

- 입력: 승인된 계획(승인 기록 포함), PR #1 diff `e8c7010..9cb009c`, HEAD 테스트.
- 출력: `notes/implementer-check-l17.md`. 코드 수정 없음.
- 계획 대비 대조 25항목: **범위 안 12 / 승인으로 해제 4 / 범위 밖 9**.
  - 승인 해제 4: 402 응답(결정 1-A-ii), 불일치 500(결정 3-a), 관리자 `catch → []` 제거(결정 3-a), `deriveDisplayStatus()` 삭제(결정 4-b).
  - 범위 밖 9: 결제 성공 시 재고 재검사·차감(#8), `src/inventory.ts` 신설(#16), 주문 생성 시 재고 미차감·부족 409(#17), payments의 `try/catch → 200` 제거(#9), `parseCardToken()` 정리(#7), 재고 테스트 7개(#21), 정책 문서 3개 수정(#23), `pending-decisions` 수정(#24), 구현 기록 신설(#25). implementer는 이들이 **무승인 변경이 아니라 먼저 승인된 `notes/order-status-plan.md`의 범위**임을 함께 적고, 분류 판단을 reviewer와 사람에게 넘겼다.
- 시나리오 ↔ 테스트: S3 충족, S6 승인 해제(반대 방향 단언 존재), S1·S2·S4·S5는 **부분**(사유 정확값 `card_declined` 미단언, 재결제 거부 메시지 미단언, 단건 조회 본문의 토큰 비포함 미단언 등), **S7(불일치 500) 테스트 0건**.
- 실행: `npm test` 29 통과, `typecheck`·`lint` 통과, 토큰 유입 grep 통과(admin/store/실패 기록 경로에 `cardToken` 없음). 미실행: 500 응답의 실제 재현.

관찰: 계획을 쓴 주체와 다른 주체가 대조하니, 단일 세션에서는 「당연히 포함」으로 넘어갔던 변경 9건이 「이 계획에는 없다」로 드러났다. 이것이 역할 분리의 실제 효과다. 다만 그 9건 자체는 다른 승인 계획에 근거가 있어, 문제는 코드가 아니라 **계획 문서가 둘로 나뉘어 있다는 것**이었다.

### 3. reviewer

- 입력: 요청, 승인된 계획, PR #1 diff, 구현 기록, 정책 3개, `AGENTS.md`, HEAD 테스트.
- 출력: `notes/reviewer-findings-l17.md`. 코드 수정 없음. 동작 확인은 `src`를 건드리지 않는 스크래치 프로브(supertest)로 했다.
- 결과: **차단 5건, 권고 9건**, 머지 가능 판정 보류(단, PR #1은 이미 머지돼 있어 사후 결정 성격).
  - 계획 이탈 PD-1~3(차단): 재고 묶음(`src/inventory.ts` 신설, 주문 생성 시 재고 미차감·409, 결제 시 재검사·차감)이 Lab 17 계획의 변경 범위 표에 없음. reviewer는 선행 계획 `notes/order-status-plan.md`에 승인 근거가 있음을 함께 적고 「범위 밖으로 기록」을 권장.
  - 테스트 누락 (a)(차단): 관리자 목록 데이터 불일치 → 500 경로를 단언하는 테스트가 0건. 누가 `catch → []`를 되살려도 테스트는 통과한다.
  - 테스트 누락 (b)(차단): `failure.reason`이 `expect.any(String)`로만 검사되어 `card_declined` 정확값과 「안전한 사유 코드만」 규칙이 미검증.
  - 권고: payments 구조 변경(PD-4), 계획 밖 테스트 7개(PD-5), 정책 문서 갱신(PD-6), 토큰 비노출 검사 범위(c), FAIL 토큰 재시도·거부 본문(d), ISO 8601·행 수·409 본문 미단언, **PI-1** Express 기본 에러 핸들러가 비프로덕션에서 스택을 본문에 싣는데 JSON 에러 미들웨어가 없음(현재 입력으로 도달 경로는 못 찾음), PI-6 원본 `Order` 직렬화.
  - 정책 이탈: 대조한 문장에서 발견 없음(부재 증명 아님, 대조 목록은 보고서 「확인한 범위」).
  - 민감정보: 응답·로그 어디에도 토큰 없음, `console.log(e)` 제거는 개선.

결론: 단일 세션은 빠르고 결과도 정책에 맞았지만, **「계획에 있었나」와 「테스트가 그 동작을 보호하나」를 검사한 주체가 없었다.** 역할 분리는 그 두 질문에 답을 만들었고, 답의 대부분은 「코드는 맞지만 문서와 테스트가 뒤처졌다」였다. 역할 이름만 바꾼 것이 아니라 입력(기준 코드 커밋, 승인 기록, diff 범위)과 금지(코드 수정 금지, 보류 확정 금지)를 달리 준 것이 차이를 만들었다.

## 남은 위험

- **Lab 전제와의 차이**: 소유자 결정으로 `deriveDisplayStatus()`를 정책대로 교체했으므로 Lab 17 E2 「diff 없음」·E4 「표시 상태의 기존 위험은 남아 있다」는 이 fork에서 성립하지 않는다. Lab 18의 VOC 출발점(잘못된 표시 상태)은 다른 관찰 가능한 결함으로 바꿔야 한다. 후보: PI-1(스택 노출 가능성) 또는 S1·S4·409 본문 미검증.
- **PI-1**: 처리되지 않은 예외가 Express 기본 핸들러로 가면 비프로덕션에서 스택이 HTML 본문에 실린다. 현재 입력으로 도달하는 경로는 찾지 못했지만(전수 증명 아님), 보호가 코드가 아니라 가정에 기대고 있다.
- **계획 문서 이중화**: `notes/order-status-plan.md`와 `notes/plans/l17-admin-failure-reason.md`가 같은 변경을 다른 범위로 적고 있다. 다음 작업은 하나의 승인 계획만 입력으로 삼는다.
- **Lab 9~16 산출물 부재**: 누적 셀프체크(`node labs/tools/check.mjs 17`)는 Lab 17 파일 4개가 있어도 이전 lab 파일 16건 때문에 실패한다. 이 fork는 Lab 12~16의 코드 변경 대신 2026-10-16 PR #1~#3으로 같은 목적지에 도달했으므로, 셀프체크의 실패는 형식 미비이지 동작 결함이 아니다.
- 테스트 보강(결정 표 4~7)은 반영됐다. 불일치 500 경로(0개·2개·사유 누락), `card_declined` 정확값, 전 응답 토큰 비노출, FAIL 재시도 거부가 테스트로 보호된다(`npm test` 36개).
